## Anti-patterns Hall of Shame

Read this list once and **internalize**. These are the patterns that get caught in code review and force rework. Most of them stem from the same root cause: **trying to solve a problem that the platform already solves**, or **not reading the platform docs first**.

### Backend / Database

| ❌ Anti-pattern | ✅ Correct approach |
|---|---|
| Inventing REST endpoints that don't exist | Read `entity/<name>/rest.sql` — all endpoints are already there. Use them. |
| Guessing field names or types in views | Read `entity/<name>/view.sql` and `table.sql` — never assume. |
| Writing classical-RESTful query strings (`?status=active&limit=10`) | The framework has its own `search`/`filter`/`reclimit`/`recoffset`/`orderby` JSON system with **20 compare operators** (EQL/NEQ/LSS/LEQ/GTR/GEQ/GIN/AND/OR/XOR/NOT/ISN/INN/LKE/IKE/SIM/PSX/PSI/PSN/PIN) plus `IN`/`NOT IN` via `valarr`. Read `wiki/13-Query-Parameters.md`. |
| Custom search/filter functions that duplicate the query parameter framework | Use `api.list_<entity>(pSearch, pFilter, ...)` with the JSON parameter system. |
| New API endpoint to compute a metric ("count active items") | Existing `/list` + `/count` with filters covers 30–40% of "I need to add an endpoint" cases. Try filters first. |
| HMAC-in-SQL for cryptographic signatures | Crypto belongs in a C++ process (e.g., `process-ESign`). The DB calls out via `api.run()` hook (observer pub/sub) or LISTEN/NOTIFY. |
| Password verification in PL/pgSQL | OAuth2 + AuthServer + 3-layer ACL handle this. Don't write password logic in the DB. |
| Hand-rolled cron functions inside PL/pgSQL | Use the platform `scheduler` (interval reference such as `EACH_05_MINUTES`) + `program` (SQL body) + `job` (`CreateJob(...)`). **There is no cron expression** — schedulers are intervals. Process-TaskScheduler polls `api.job('enabled')` once a second and drives the job's own state machine. |
| Familiarization / acknowledgement as a custom table | Use `db.object_link` (link entity = user, type='acknowledged') — it's already designed for this. |
| Over-loaded entity dispatcher with 24+ unrelated routes | Split by class hierarchy. Each subclass = its own directory + its own `rest.sql`. |
| `UPDATE` on append-only journal/audit-style entries | Immutable entities use a **custom workflow with no `edit/save/update` methods**. State stays `created` forever. Corrections via a separate `correction_entry` row referencing the original. |
| Calling `AddDefaultMethods()` for an immutable entity | `AddDefaultMethods()` adds `edit`/`save`/`update`/`enable`/`disable`/`delete`/`restore`/`drop` — wrong shape for journal entries. Write a custom `Add<Entity>Methods()` instead. |
| Custom action without `ChangeObjectState()` event | Standard actions (enable/disable/delete/restore) handle their state transitions automatically. **Custom actions** (e.g. `submit`, `available`, `correction`) **require** an explicit `'ChangeObjectState();'` event registration in addition to your `Event<Entity><Action>();` event. Otherwise the state never changes. |
| `parent FIRST → entity SECOND` for delete/drop | Wrong. For **destructive actions** (delete, drop) it's **entity FIRST → parent SECOND** so the entity can clean up specialized rows / cascade children before the parent's FK cascade fires. |
| Missing `Access<Entity>` view | Every entity **must** have an `Access<Entity>` view filtering by `db.aou` mask `B'100'` — one per `Object<Entity>`, no exceptions. The join itself is attached **at runtime by `api.sql('kernel', …)`**, so `Object<Entity>` must *not* join it inside (that is the old static model — see the callout in Step 7). A missing pair raises no error: the platform silently omits the join and access control disappears. |
| Forgetting `SECURITY DEFINER` on kernel/api functions | All functions in `kernel`/`api`/`rest`/`daemon` schemas need `SECURITY DEFINER` + `SET search_path = kernel, pg_temp` (or domain-appropriate). Without these, RLS won't work and search_path injection becomes possible. |
| Skipping `CheckJsonbKeys()` validation in REST dispatcher | Every `rest.<entity>` route with `pPayload` must validate keys via `CheckJsonbKeys(pPath, arKeys, pPayload)`. Otherwise typos and unknown keys are silently ignored. |
| Re-implementing `current_locale()` / `current_userid()` / `current_session()` / `current_area()` / `current_scope()` | Platform `current` module gives all session-context functions. Use them, don't compute manually. |
| Hardcoding state codes / method codes / action codes in app code | Use `GetState(pClass, 'available')`, `GetMethod(pClass, GetAction('enable'))`, `GetAction('submit')`. The codes are textual but the IDs are runtime UUIDs. |
| Hardcoding state-type UUIDs (`'00000000-0000-4000-b001-000000000002'::uuid` for 'enabled' etc.) | Use platform helpers: `IsCreated(pObject)`, `IsEnabled(pObject)`, `IsDisabled(pObject)`, `IsDeleted(pObject)`, `IsActive(pObject)` (true for created OR enabled). Reading state code: `GetObjectStateCode(pObject)` ('available'/'unavailable'/...) or `GetObjectStateTypeCode(pObject)` ('enabled'/'disabled'/...). |
| `PERFORM ExecuteObjectAction(pObject, GetAction('enable'))` everywhere | Use the named wrappers: `DoCreate`, `DoEnable`, `DoDisable`, `DoDelete`, `DoRestore`, `DoDrop`. For non-standard actions: `DoAction(pObject, 'available')` — takes the action code text, calls `GetAction()` internally. Reads cleaner and is what's documented. |
| Calling `enable` on a freshly created entity inside a helper | `Create<Entity>()` (CreateStation, CreateClient, …) **already** runs `enable` internally — the new row lands in `unavailable`, not `created`. Don't call `DoEnable` again or you'll get *"method not found for action enable in state unavailable"*. Just `DoAction(uObj, 'available')` from there. |
| `CREATE OR REPLACE FUNCTION` after changing a parameter type or set | PostgreSQL treats this as a new overload, not a replacement — the old function lingers. Drop the old signature with `DROP FUNCTION IF EXISTS xxx(text, text, uuid)` (full signature) — **in a patch**, not in `routine.sql`/`api.sql`/`view.sql`: those run on every install and update and stay `CREATE OR REPLACE` only (the files are re-run, a patch runs once). Same for OUT-parameter changes — they alter the return type, which `OR REPLACE` rejects. **A brand-new function with no old form needs no patch.** **A new parameter with `DEFAULT` while the old form still exists** makes every call by the old form fail with *"function … is not unique"* — the base right after `--update` without the patch is exactly that. On a hot path, `DROP` + `CREATE` go **in one transaction in the patch**, so no caller sees the gap. |
| `FOR i IN 1..array_length(a, 1)` | `array_length` is NULL for both NULL and `'{}'`, and a NULL loop bound raises. Use `coalesce(array_length(a, 1), 0)`, `FOREACH` or `unnest`. When you make a raising function return NULL instead, check every caller first: `'…' \|\| NULL` and `array_to_string(NULL, …)` are NULL, so the error turns into a SQL clause that silently disappears. |
| Seeding a service or system user with a literal password (or password = login) | `CreateUser` with an empty password derives an unknown one (`admin/routine.sql:3847`); a literal in a seed loses that and lands in git. |
| Relying on `EXCEPTION WHEN OTHERS` to keep a secret out of the error `CONTEXT` | `OTHERS` does not catch `query_canceled` or `assert_failure` — name them. A `WARNING`'s `CONTEXT` reaches the server log past any handler. A `NULL` in `RAISE … USING` is itself an error. |
| `SELECT … FROM a LEFT JOIN b ON … FOR UPDATE` | PostgreSQL refuses: *"FOR UPDATE cannot be applied to the nullable side of an outer join"*. Use `FOR UPDATE OF a` (lock only the inner table) or split into two SELECTs. |
| Hand-coding raw SQL casts for *codes* coming from C++ (e.g. `'%s::uuid'` with a region code) | Daemon-side identifiers are usually **codes** (text, e.g. region "55", from env vars). Don't cast to uuid in the SQL string — the cast happens at parse time, before function dispatch, so PostgreSQL fails on the literal even if the function would resolve it. Pass as `::text` and let the function resolve via `GetRegion(pCode)` / similar lookups. |
| Assuming `api.list_<entity>()`/`api.count_<entity>()` is fast because the underlying query "only" joins an `Access<Entity>` view with a `LIMIT` | **Known systemic db-platform planner regression** — see callout below. Don't add a bespoke per-entity workaround before reading it. |

> **Performance: `api.sql()` + `Access<Entity>` + `LIMIT` can flip Postgres to a catastrophic Nested Loop.** Verified live on a production base (2026-07-09): a `list` call with `LIMIT 500` through an `Access<Entity>` join went from 54ms to 7.9s (≈150-240×) on real data. Root cause: the `HAVING (bit_or(allow) & ~bit_or(deny)) & B'100' = B'100'` in every `Access<Entity>` view can't be estimated by the planner, so the join is misestimated at `rows=1` — combined with `ORDER BY … LIMIT`, the planner picks a cheap-startup Nested Loop that re-executes the expensive side once per row. **Systemic**: `api.sql()` generates this join shape for *every* `api.list_<entity>()`/`api.count_<entity>()` whenever an `Access<Entity>` view exists; default `LIMIT` is 500. **This is insurance against a rare catastrophic plan, not an optimisation — verified 2026-08-24: with the order of runs alternated, `on≈136ms` vs `off≈135ms` on 3000 rows, indistinguishable.** An earlier "6% faster" measurement turned out to be warm-up handed to whichever mode ran first. Apply it where you accept the risk, not everywhere. **Do not reach for `enable_nestloop` at all** — that was the obvious fix and it is the wrong one, established 2026-08-24. Two reasons. First, scope: `set_config('enable_nestloop','off',true)` and `SET LOCAL` share the **transaction**, which is not the request — `api.run` is an ordinary function, so one HTTP call is one transaction and a batched payload loops inside it; the whole batch then runs without nested loop, including the key lookups that need it. Confining it to one query means saving and restoring the previous value around the `EXECUTE`, and `api.sql()` has no `EXECUTE` — it `RETURNS text`, and the `EXECUTE` sits in ~116 hand-written per-entity wrappers. Second, and decisive: **the planner is chasing a benefit that cannot exist.** `Access<Entity>` is a *blocking aggregate* (`GROUP BY … HAVING bit_or(…)`) — it physically cannot return a first row before it has computed all of them, so the cheap-startup plan a Nested Loop is chosen for is unreachable by construction. **Take away the illusion instead of forbidding the plan:** where `api.sql()` builds `vJoin`, emit `WITH aou AS MATERIALIZED (SELECT object FROM kernel.access<x>)` and join that. One place to change — the single function that knows about `vJoin` — scope is one query rather than a transaction, no GUC is touched so nothing needs restoring, and the wrappers stay untouched. Materialising costs nothing: the aggregate was going to be computed in full anyway. **Since db-platform 1.2.20 upstream does exactly this** (`api/api.sql:213` at 1.2.31: `WITH aou AS MATERIALIZED`); a project pinned below 1.2.20 has no fix of any kind — check yours before you assume: `grep -n MATERIALIZED sql/platform/api/api.sql`. Any change to it is framework work: route it through `/apostol`.

### Frontend

| ❌ Anti-pattern | ✅ Correct approach |
|---|---|
| Storing tokens in `localStorage` / `sessionStorage` | **Cookie-only.** Cookies are `HttpOnly` — JS can't read them. XSS-safe. The server side refreshes an expired access token from the cookie — see the next row for who. |
| Tracking `expires_in` and scheduling a refresh in JS | Don't. **Who refreshes depends on the path:** `/api/v1` — AppServer (`check_auth` → `token_refresh_and_fetch`, `AppServer.cpp:393–411`); `/api/v2` — `GatewayAPI`, which *is* an AppServer and inherits `check_auth` (`GatewayAPI.hpp:52`); a standalone SPA served by its own process without AppServer (e.g. a device console) refreshes itself on 403 — then every 403 costs it a `/oauth2/token` round-trip. Know which one your page talks to. |
| Writing token-refresh logic in JS | Behind AppServer/GatewayAPI — already handled server-side. Only a SPA with neither behind it owns this logic. |
| Sending `Authorization: Bearer` header from a browser SPA when cookies are available | Cookies + `credentials: 'include'` are simpler and safer. Bearer header is for server-to-server / native apps. |
| CORS misconfiguration (allow-all-origins) | Origins must be in `conf/oauth2/<provider>.json` `javascript_origins` allowlist. |
| Minting a service session in the browser (`client_credentials` from the SPA, `X-Auth-Context: service`) | A public client cannot hold a secret (RFC 6749 §4.4). Guest routes are called anonymously and executed by AppServer with its own confidential token — Step 10, the service-session callout. |

### Process / Code organization

| ❌ Anti-pattern | ✅ Correct approach |
|---|---|
| Modifying anything in `sql/platform/` (under `db/` or `backend/db/`) | **Never.** Platform is shared infrastructure. If you need a fix there, push it upstream first via `/apostol`. |
| Modifying anything in `src/lib/libapostol/` (`src/lib/delphi/` on v1 projects) or upstream module sources | Never. Same rule. |
| Modifying `apostol-repo-v2/` mirrors | Read-only mirrors of upstream. They're **never** the source of truth — the actual code is in the project after `git submodule update`. |
| Editing reference projects (another team's configuration, `apostol-crm`, etc.) | Read only. Use them as the reference for "what does production actually look like". |
| Branching out without updating `INDEX.md` after adding a new entity | Keep `configuration/<dbname>/INDEX.md` in sync. The next agent (or you in three months) will need it. Drift compounds silently — a stale-scan on a real project once found **47 entity `INDEX.md` files up to 139 days out of date** after a multi-week feature push, several describing whole subsystems as "not implemented" or "planned" when they'd shipped weeks earlier. Regenerating isn't just cosmetic: comparing old INDEX.md prose against current SQL surfaced several *real* bugs along the way (a workflow event wired to a function that no longer exists, a dead exception path, a class registration referencing a type nothing creates). Use the **`/index`** skill's stale-scan mode (mtime-based, default behavior) periodically — not just "when I personally touched this entity" — and treat its diff as a lightweight code-review pass, not pure documentation busywork. |
