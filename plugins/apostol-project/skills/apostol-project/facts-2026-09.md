## Step 17 — Facts established by the 2026-09 inventory (read before trusting older text)

Source: an inventory of 73 findings measured against db-platform **1.2.20** and seven production
configurations. Each line below overrides anything older in this
skill or in the wiki that says otherwise.

### Workflow engine

- **Methods are not inherited.** `GetMethod` walks up the class tree only through **non-abstract**
  classes, and `object`/`document`/`reference`/`message` are abstract, so the walk stops at once.
  Every concrete class must carry its full method set (19 with `AddDefaultMethods`). A subclass
  that relies on the parent's methods gets `MethodActionNotFound`.
- **The state change is a handler, not the engine.** `ChangeObjectState()` is registered as an
  ordinary `event` on six actions (`create enable disable delete restore` — and **not** `drop`). For
  every other action the configuration registers it itself. Its **position** among the handlers is
  not unified: for `job` it runs before `EventJob*` on `execute/done/fail/abort/cancel` and **after**
  on `complete` — so a handler may see the old or the new state depending on the action. Decide and
  document the order per action.
- `deleted:restore` goes to **`created`**, not `enabled` (the wiki says `enabled`).
- Default labels from `AddDefaultMethods` are `Created / Opened / Closed / Deleted`, not
  Enabled/Disabled. `AddDefaultMethods(class, namesEN, namesRU)` expects **9** names; most
  configurations pass 7 and get `GetActionName()` for the rest.
- `AddEvent(class, type, action, **pLabel**, pText, …)` — the function name is the **5th** argument
  (`'EventX();'`), not the 4th as two wiki pages show. `RegisterRoute('x', AddEndpoint('SELECT * FROM rest.x($1, $2);'))`
  — the 2nd argument is an endpoint uuid, not a string.
- `db.method_stack` rows are never deleted after execution; `EventObjectDrop` is the only cleaner.
- **Pass parameters to a nested action through `pParams`, not through `db.object_data`.** Several
  projects write `change`/`hidden`/`bindingId` rows before `ExecuteObjectAction` and read them inside
  the handler — it works, and it is the mark of a missing typed parameter; do not copy it into new code.

### Context and session

- Context (`current.*`, `context.*`) is `set_config(…, false)` — **session-scoped**: it survives `COMMIT`, and on a
  pooled connection it reaches the **next request**. What clears it depends on the entry point (corrected 23.10.2026):
  libapostol PgPool resets the names listed in `postgres.reset` before every query (default `["current.area"]`, since
  libapostol `788d4e1` — check your pin); `daemon.begin` (GatewayAPI) runs `ResetGatewayVars`; otherwise only the next
  `SessionIn` / `InitContext`. A function that calls `SetCurrentArea` restores it on **every** exit — a plain `RETURN`
  leaks it. Like any `SET`, the context is undone by `ROLLBACK` (and by the rollback of an `EXCEPTION` block): an error
  between `EnterSystemContext` and `LeaveSystemContext` leaks nothing — a normal return that skips `Leave` does. Some
  state lives on the connection on purpose (a cached session): before you widen a reset, find its readers, in SQL and in
  C++. Never run the application through a transaction-pooling `pgbouncer`; never read `context_object()` outside a
  running action.
- `SubstituteUser` changes `userid`, not `suid`, and **does not re-evaluate `SetAccessMode`**:
  `EnterSystemContext` runs with the access mode of the client it signed in as.
- `GetAccessMode()` defaults to **true** (filtering on); it is set false only for members of
  `administrator` at `SignIn`/`SessionIn`.
- **A session code is a full credential.** `api.authorize(code)` establishes the context from the
  40-char code alone; C++ builds SQL by string interpolation, so codes land in `postgres.log` when
  statement logging is on. Never log them; never put them in URLs you keep.
- `daemon.authorized_fetch` (HTTP Basic) **creates and deletes a session on every call** — four rows
  in `db.session`/`db.token*` per request. Do not use Basic for integrations; use a service session.
- A session per **message** (instead of per connection) serialises the whole fleet on one tuple lock
  and grows `db.oauth2` without bound. One session per **connection**.
- Token expiry is checked from `db.token`, not from the JWT `exp` claim; revocation = deleting the
  row. Consequently a Bearer cannot be validated without the database.

### Access

- The six checks live at five altitudes and **nothing verifies they agree**: `db.acl` (17 bits,
  consulted only inside `admin/routine.sql`, absent from REST), `db.acu` (copied into AOU at INSERT
  only — later ACU changes do not reach existing objects), `db.aou`+`db.aom` (owner always ends with
  `B'111'`; the AOM group triplet is unreachable from a session), `db.amu`→`db.oma` (a read-shaped
  check that **INSERTs** and is **never invalidated** on group-membership change), `DocumentAreaTree`
  (a join inside `Object<X>` — absent from every path that bypasses the view and from all direct
  writes).
- Statements on the **kernel pool skip object-level write checks at trigger level** (`session_user IN
  ('kernel','postgres')`). Background code running as `kernel` is not protected by the barrier.
- There is no tenant in the platform model. A tenant gate is a **configuration override** of
  `CheckObjectAccess` / `CheckObjectMethodAccess`; make it **fail closed** — an object whose tenant
  resolves to NULL (every non-document, unless you say otherwise) must be denied, not allowed.
- Do not replace the access join with an explicit `tenant = current_tenant()` filter: measured on a
  real configuration, it **widened** access — a restricted role gained rows across 21 entities. The
  explicit filter is broader than the ACL it replaces.
- Performance: `Access<X>` is a blocking aggregate the planner cannot cost. 1.2.20 wraps it in
  `WITH aou AS MATERIALIZED` — insurance, not a speed-up. `enable_nestloop=off` was withdrawn.
  A view that is deliberately left without the access join needs a written, audited reason and a
  shelf life; a view joining more relations than `from_collapse_limit` is planned badly.

### Request path and errors

- `api.run` truncates the path to the **third** segment before dispatch and logging
  (`/api/v1/user/get` → `/user/get`), and appends `{"reclimit": 0}` for `/count`.
- **No `rest.*` in the platform has an `EXCEPTION` block**: a batch payload is all-or-nothing, and
  the error does not say which element failed. Only `/run` isolates elements (each through a nested
  `api.run`), and its `key` counter is NULL by a declared-without-value bug.
- `ParseMessage` is positional: `RAISE EXCEPTION 'ERR-40000: …'` (17 sites in one configuration) collapses to
  `ERR-400-000`, a code in no catalog. Use `ERR-GGG-CCC: ` exactly.
- Only `401/403/404/500` reach the client as HTTP status; **every other code, including `ERR-409-*`
  and `ERR-429-*`, is sent as HTTP 400**. `POST /api/v1/ping` answers 400 for the same reason.
- `db.api_log` is never cleaned (`ClearApiLog` has no caller); `AddApiLog` is overridden in **all
  seven** configurations. If you override it, keep the platform's full redaction list
  (`oldpass`/`newpass` and the rest) — dropping it writes passwords into the log.
- `api.get_method_spec` does not exist; OpenAPI, where a project has one, is generated outside the
  database from the `rest.sql` `WHEN` branches (a project script, not part of the platform), and response schemas are
  generic because the field set lives only in `api.<x>` views at runtime.

### Extension mechanism

- The platform has **15 `Do*` hooks** (`DoLogin/DoLogout`, `Do{Create,Update,Delete}{Area,Role}`,
  `DoConfirmEmail/Phone`, `DoFCMTokens`, the four observer `Do*Listener*`). `DoDeleteUser` does not
  exist. `DoFilterListener` returns **false by default** — a project that does not override the four
  observer hooks has subscriptions that never deliver.
- Every project also redefines **30–76 platform names** by `CREATE OR REPLACE` later in the load
  order; 27 non-hook names are redefined by ≥2 projects (`AddApiLog`, `CheckSession`, `locale_code`,
  `current_locale`, `http.get/post`, `RecoveryPasswordByEmail`, `api.sql`, `CheckObjectAccess`…).
  The mechanism is **silent**: nothing records which body won. To know, read `pg_proc.prosrc` on the
  running database, not the files. Mark every deliberate override with a comment *inside* the body.
- The 18 platform lifecycle handlers `EventObject*`/`EventDocument*` are redefined with empty bodies
  by all seven projects to silence `WriteToEventLog` — expected, not a bug to fix.
- `api.signup` exists in no platform and in all 7 configurations; `GetObjectTenant` was invented
  twice, by two projects, under the same name.

### Lifecycle and dead weight

- `platform/patch/patch.psql` is **entirely commented out** and lists 12 of 18 `v1.2` patches;
  `runme.sh --patch` applies **zero** platform patches. `db.patch_log` is created by `db/migrate.sh`,
  not by `install.psql`.
- `./runme.sh --test` is advertised twice and implemented nowhere; there are no pgTAP tests. Projects test
  from outside (e.g. pytest against a throwaway install).
- `rest.event '/event/log'` has been broken since 2026-04 (4 args against a 5-parameter
  `api.user_log`).
- `reports/` registers nothing (its `init.sql` files are 0 bytes); `comment` has no caller and 0 rows;
  `kladr` tables are empty everywhere; `resource`'s "tree" is flat (147 of 148 nodes are roots).
- `CONFIG\CurrentProject` is misspelled as `CONFIGCurrentProject` in four places of `file/table.sql`
  — every stored file URL loses its host prefix.
- PGFile has **no polling fallback** (alone with WebSocketAPI) and discards the `hash`/old path from
  the NOTIFY payload: a renamed file keeps its old copy on disk forever.
- PGFetch has no queue cap; a lost `LISTEN` subscription once cost 11 h 15 min and 142 unsent
  requests. Any new LISTEN consumer needs a poll.
- `module.<Name>.enable` is the key the code reads; several READMEs say `modules.<Name>.enabled` —
  neither spelling in the README does anything.
